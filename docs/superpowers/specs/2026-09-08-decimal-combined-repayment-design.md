# BigDecimal 账本与合并还款

用户已认可：高精度用于计算及未结算记录，正式人民币入账精确到分；要求同时解决到期款与额外提前还本分开操作的问题。基线 `510754f`，同一 Stage 2 工作区，不清库、不另开分支。本轮实现与验证不等于推送或发布。

## 可验收的用户结果

1. 账本核心金额使用 BigDecimal，正式余额/借贷金额以元为单位、两位小数存储；旧金额、来源、凭证、请求回执和报表结果保持一致。
2. 贷款计算保留高精度和可追溯的分币尾差；不因正本金逐期约束把等额本息改成等额本金。允许合理的零本金、正利息期次，不允许零现金空期次。
3. 根据原剩余到期日、实际本金、利率、还款方式及用户提供的合同最低常规月供，计算真实可生成的期数集合。没有合同数据时明确只是本系统测算，不编造“低于10元最多12期”等银行规定。
4. 一个确认页面处理截至实际还款日全部已到期未付本息及额外提前还本；确认前展示完整总额，任何一步失败整笔回滚。
5. 当前/历史计划、现金余额、费用、本金、合并操作明细和跨模块汇总保持一致；网络不确定时原请求可重放，升级前旧请求仍能核对结果。

## 精度与兼容边界

- 复用 JDK BigDecimal、现有账务内核和 MySQL，不引入新的账本产品或浮点金额。
- 正式金额统一归一化为 scale2；超过两位的非零小数不能静默舍入入账。`1.2300`可规范为`1.23`，`1.231`拒绝。正式分录借贷精确相等，现金和贷款本金不能透支。
- 高精度计算使用显式 MathContext DECIMAL128，持久化测算金额/尾差用 DECIMAL(30,12)。公式运算不在每个中间步骤截到两位。首末期、尾差分配采用版本化规则。
- 核心数据库用 DECIMAL(21,2) 主金额列；保留既有有符号long分范围，避免兼容读溢出。旧`*_cents`列可改为单向只读生成列，仅用于过渡查询；不是第二份可写余额。不得留下两份独立金额真相。
- Core Java DTO/store/余额重建/过账/冲销使用 BigDecimal。旧业务模块、旧HTTP金额字符串与Cents接口通过精确边界适配保留；不把本轮称为全项目所有数值字段迁移。贷款核心实体金额同步改为BigDecimal，其他业务实体的整数分是兼容边界。
- 原二进制凭证摘要保持逐字节兼容：金额在摘要边界转换为原整数分编码；不改写旧摘要。新小数金额等价表示规范化，不使用double构造BigDecimal。
- 迁移逐分等值转换，不改账务意义，不回算历史已付或既存待还计划，不删除业务记录。新增迁移从V22起，旧V1–V21不改。

## 高精度计划与可选期数

- 使用精确理论本金/利息轨迹，单独保存每期的理论金额、实际分币金额和舍入差额。旧期次缺少理论记录时，以原已确认分币金额作为精确已结算基线，不猜测旧亚分债权。
- 标准等额本息优先保留两位小数的常规月供和尾期调整；若这种方式不能保持原期数，则使用高精度等额本息轨迹的累计分币分配，明确标记“分币尾差调整，各期可能相差少量分币”。不能变成每期强制一分本金。
- 累计本金向下保留到分，末期分配全部剩余本金，以保证不会提前出现本金已清零而后面仍留空期次。利息按完整非负累计精确利息舍入，再减此前已结算利息；不能对孤立负carry再次HALF_UP造成半分钱重复退款。实际本息为这两部分相加。
- 跨重算以已付理论利息与已付实际利息组成结算基线；取消的未来期次不计入。终结时亚分尾差按累计结算规则处理，留下结算差异记录，不藏在现金或本金余额里阻止关闭。
- 正式支付允许本金为0、利息为正，但必须有正现金合计；对应凭证不生成零金额本金分录。实际贷款本金仍保持两位，最后的正本金期次才结清本金。
- REDUCE_TERM保留原逐期付款上限；REDUCE_PAYMENT保持当前未来期数；新增ADJUST_TERM允许用户显式选择更短期数。修改期数后不再标成“期限不变”。所有方案沿用原未来日期前缀，绝不延长原到期日。
- 合同最低常规月供可选录入，只有用户提供才约束生成计划，尾期结清可低于常规最低额并明示。单独的贷款还款规则接口保存参数与来源说明，不增加旧创建请求的摘要歧义；修改规则使旧报价失效，不改变旧期次。
- 可选集合逐个试算1..当前未来期数（最大360），过滤零现金期次、不能按原模型还清、违反用户合同规则的结果；集合连续时UI可显示范围，不连续时展示实际选项。无有效分期时仍提供原有一次结清入口，而非生成空计划。
- 3.60元/年12%/360期的高精度等额本息应能形成正现金的360期分币计划，本金合计3.60，末期本金归零，绝不退化为每期固定0.01本金。0.01元零息不能生成多个正现金期次，UI应主动提供可行期数而非提交后才报错。

## 到期款与额外还本合并

- 新增只读`GET /api/loans/{id}/repayment-preview`与`POST /api/loans/{id}/repayment`。新请求字段明确为`additionalPrincipal`，含实际日期、实际付款账户、strategy、可选targetPeriods、planToken、idempotencyKey。
- 新流程默认把dueOn<=paidOn的所有PENDING期次纳入结算，`additionalPrincipal`是除此之外额外偿还的本金。输入额外本金必须为正，且不能超过结清到期期次后的剩余本金；恰好等于时允许一次确认结清剩余本金，不要求再跳转重填。
- 预览包含到期列表、到期本金/利息合计、额外本金、本次总本金、本次总利息、本次总现金、账户余额及预计余额、未来计划前后对比、可选期数和完整token。
- 示例：剩余本金10000，到期本金1000/利息100，额外本金3000，总现金4100；账户5000→900、本金10000→6000、费用100。账户4099.99则无任何成功记录，不能先成功扣1100再报失败。
- 同一事务内允许分别生成原有LOAN_PAYMENT凭证/流水和额外LOAN_PREPAYMENT凭证/流水，保留原来源与报表口径；“一次确认”不要求合并成一张含混凭证。新增不可变合并操作记录关联各子操作，回执重放返回同一个合并结果，历史汇总只计子流水一次。
- 不调用会再次授权并清空EntityManager的公开确认接口来循环付款。提取已授权、已锁定事务内部的期次结算协作者，普通按期确认与合并流程共用。
- 权限不提升：提前还本沿用OWNER/ADMIN；若含到期期次，还需原有指定确认人权限。权限在预览和提交都检查，未授权不能因为合并而绕过。
- 锁顺序保持家庭优先，提交读取当前贷款/期次/账户，核对本金投影、实际日期和每日期末现金不为负。预览一致RR快照；token绑定全部到期与未来期次、精度元数据、规则、金额、日期、账户和策略。
- 整体回执优先于关闭状态/变化计划检查；子请求键由父键确定性派生且不超过100字符。任何中途异常回滚所有子操作、批次、分录、回执和通知状态。
- 老`/prepay`和按期确认路径保留请求/摘要兼容，不给旧请求偷偷加上额外到期款。新界面改用明确合并接口；旧请求在存在到期款时仍可返回引导提示。

## UI与验收

延用Clarity样式、当前/历史视图、草稿保护、焦点、窄屏可访问和跨模块刷新。输入标签“额外提前偿还本金”；本期本息与额外本金清楚分列；确认按钮含总现金金额。选择日期/账户/金额/策略/期数/合同规则后重新预览并排除旧响应。模糊网络结果冻结原请求和金额明细，不因重新预览而丢失核对入口。

验证包含：旧库升级余额/分录/回执完全对应，BigDecimal正式精度拒绝，真实MySQL并发不透支，标准/CUSTOM/零利率/亚分尾差、利息期、动态期数，合并中途失败全回滚与重放，角色隔离、已付历史、预算/年度统计费用不含本金，真实浏览器普通和360px流程。测试只用隔离库，无生产写入。

规则依据：[工行公开住房贷款合同](https://media.icbc.com.cn/agreement/1214784522797809665.html)将最低还款额和提前还款条件放在具体合同中；[BigDecimal](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/math/BigDecimal.html)提供显式精度与舍入；[MySQL DECIMAL](https://dev.mysql.com/doc/refman/8.0/en/fixed-point-types.html)存储精确十进制。上述是设计依据，不声称系统给出银行审批或正式结清报价。
